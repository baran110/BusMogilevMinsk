# БЖД: уточнение плана обновлений

Статус: предложение на согласование владельцем. Описанная ниже независимая схема ещё не внедрена. Настройки коротких запросов исправлены отдельно; production не менялся.

## Причина изменения

Полный реальный сбор с ограничением шесть минут подтвердил 17 из 60 сочетаний даты/направления. Запрос с успешной повторной попыткой занимал обычно 40–47 секунд. Ближайшие три даты в обе стороны подтверждены примерно за 127 секунд. Изменение одного таймаута не решает регулярное обновление всех 30 дней.

Продление общего коллектора до десятков минут задерживает ближайшие предложения остальных источников. Поэтому рекомендуется оставить их существующую цепочку и вынести долгий сбор БЖД в отдельный процесс того же GitHub Actions. Новый сервер или платный сервис не требуется.

## Рекомендуемая схема

1. Ближний сбор БЖД выполняется каждые десять минут, сохраняет результат трёх дат в промежуточный ключ KV. Основной collector получает свежий результат перед публикацией общего снимка. Ошибка БЖД не отменяет сбор остальных источников.
2. Отдельный дальний workflow работает раз в час. Он проверяет оставшиеся 27 дат пакетами по пять дат, оба направления. Каждый пакет сохраняется сразу после проверки, без ожидания конца месяца. У дальнего процесса одно одновременное обращение к БЖД; у ближнего не больше двух. Общая нагрузка ограничена тремя одновременными запросами; запреты и длительный Retry-After прекращают запросы.
3. Основной collector читает проверенные пакеты. Для каждой даты выбирает последнее фактическое наблюдение; успешная пустая выдача, ошибка и последнее известное расписание остаются разными состояниями. Устаревшие цены и места не становятся доступными из-за новой публикации. Дальний процесс не переключает `manifest:active`.
4. Таймер отслеживает занятость каждого workflow отдельно. Долгий дальний сбор не блокирует десятиминутные циклы. Мониторинг отдельно проверяет ближнюю и дальнюю свежесть БЖД.

Полученный от владельца email хранится вне публичного репозитория. Уведомления включаются только после согласования запуска.

## Стоимость и ограничения

Оценка записей KV: существующие 480 в сутки, плюс 144 ближних результата БЖД и примерно 144 дальних пакета — около 768 записей в сутки. Это ниже [бесплатного лимита 1000](https://developers.cloudflare.com/kv/platform/limits/), но повторы и ручные проверки уменьшают запас. Реальный бюджет проверяется перед запуском; платный тариф автоматически не включается. GitHub остаётся публичным, используется существующий набор сервисов и секретов.

По наблюдавшимся задержкам последовательный дальний сбор может занимать около 40 минут. Это оценка, а не уже измеренный результат новой схемы. Сохранение каждого пакета по мере готовности необходимо, чтобы первые проверенные даты не ждали окончания всего сбора. При устойчивом замедлении или ограничении источника обещание свежести не имитируется: показываются возраст и неизвестная доступность, срабатывает уведомление.

При 24 таких запусках это порядка 16 часов времени runner в сутки только для дальнего процесса; большая часть — ожидание сети. [Стандартные GitHub-hosted runner для публичных репозиториев бесплатны](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job). Схема не должна использовать платные larger runner, создавать большие артефакты или автоматически менять репозиторий на приватный. Сокращение ожидания через официальный источник БЖД предпочтительно, если такой разрешённый канал удастся получить.

Полный охват регулярных автобусов эта задача не решает: для них остаётся отдельное требование разрешённого источника данных.

## Альтернатива и откат

Более простой вариант — ограничить поиск поездов ближайшей неделей и явно показывать границу покрытия. Он сохраняет нынешнюю схему, но уменьшает функциональность и требует отдельного решения владельца. Для исходной цели с горизонтом 30 дней рекомендуется независимый сбор.

Откат до включения: изменения остаются в отдельной ветке, внешние процессы не включаются. После разрешённого запуска можно остановить дальний workflow, сохранив последние подтверждённые пакеты с их исходным возрастом; остальные источники продолжают обновляться. Отказ от новой схемы не должен возвращать демо-подмену или искусственную свежесть данных.
