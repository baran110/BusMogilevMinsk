# Обслуживание «Могилёв — Минск»

Это инструкция к подготовленной версии. Само наличие файлов не означает, что выпуск уже опубликован, таймер включён или все перевозчики подключены.

## Кто и чем управляет

Владелец хранит индивидуальные ключи и доступ к GitHub/Cloudflare. Пассажиры вводят выданный личный ключ и переходят на сайт продавца. Сайт не продаёт билеты и не подтверждает бронирование.

Доступ к расписанию проверяет сервер на обоих адресах. Статические файлы и минимальная проверка работоспособности открыты. Сессия действует семь дней только на том адресе, где выполнен вход. Для зеркала нужно войти отдельно. Старые записи доступа в браузере больше не действуют.

## Создание и отзыв ключей

После отдельного согласования запуска, на компьютере владельца:

```bash
pnpm install --frozen-lockfile
pnpm access:manage issue 10
```

Команда создаёт до десяти ключей в `.private-access`, без вывода значений в журнал и без отправки в Cloudflare:

| Файл | Использование |
|---|---|
| `issued-keys.txt` | Личные ключи. Передать каждому пассажиру только его строку защищённым способом. |
| `registry.json` | Реестр идентификаторов и хешей. Его содержимое — значение секрета `ACCESS_KEYS`. |
| `session-secret.txt` | Значение секрета `SESSION_SECRET`, без кавычек. |
| `cloudflare-secrets.json` | Комплект для защищённой настройки; не публиковать. |

Эти файлы исключены из Git. Не прикладывайте их к переписке, issues, PR или публичным артефактам. Не запускайте повторное создание поверх существующего реестра. Сохраните защищённую резервную копию вне репозитория.

В Cloudflare откройте **Workers & Pages → bus-mogilev-minsk → Settings → Variables and Secrets → Production**. Добавьте два секрета: `ACCESS_KEYS` и `SESSION_SECRET`. То же выполните для **mm-routes-mirror**. Используйте одинаковый реестр и секрет на двух сервисах. Сами ключи пассажиров в Cloudflare не загружаются.

Названия пунктов панели могут меняться. Если панель предлагает применить изменение через публикацию, сначала согласуйте этот шаг: это изменение рабочей инфраструктуры.

Для отзыва одного ключа:

```bash
pnpm access:manage revoke passenger-01
```

Обновите `ACCESS_KEYS` из нового `registry.json` на обоих сервисах и примените конфигурацию. После применения старый ключ и уже выданная ему сессия должны возвращать 401. Остальные ключи продолжают работать. Отзыв завершён только после проверки обоих адресов. Замена `SESSION_SECRET` завершает все сессии.

## Секреты инфраструктуры

GitHub хранит секреты через **Settings → Secrets and variables → Actions**, Cloudflare — через панель секретов. Не храните токены в исходниках.

| Секрет | Где нужен | Минимальные права |
|---|---|---|
| `CLOUDFLARE_ACCOUNT_ID` | GitHub, сбор и выпуск | Идентификатор выбранного аккаунта. |
| `KV_NAMESPACE_ID` | GitHub, сбор и диагностика | Должен совпадать с namespace в обоих wrangler-конфигах. |
| `CLOUDFLARE_API_TOKEN` | GitHub, существующая конфигурация | Текущие права требуют проверки владельцем. Для сбора достаточно KV Read/Edit в нужном аккаунте. Для деплоя нужны Pages/Edit и Workers Scripts/Edit. Предпочтительно разделить токены перед рабочим запуском. |
| `GITHUB_TOKEN` | Только секрет Worker-таймера | Fine-grained token: только этот репозиторий, Actions Read/Write; без Contents Write. Контролировать срок действия. |
| `ACCESS_KEYS`, `SESSION_SECRET` | Только Pages и Worker-зеркало | Серверный доступ пассажиров. |

Диагностический workflow не пишет KV. Хотя существующий токен может иметь более широкие права, сам этот workflow использует только GET. Не переносите его секреты в тесты PR из сторонних репозиториев.

## Выпуск

Обычный push больше не запускает production-деплой. Ветка разработки и draft PR сохраняют подготовленную работу; не сливайте PR до разрешения владельца. При наличии автоматической Git-интеграции в Cloudflare отдельно проверьте настройки веток: её правила не управляются workflow GitHub.

Перед запуском должны быть согласованы охват источников, настройка секретов и мониторинга, а также проверена доступность из Беларуси. Нельзя объявлять все виды транспорта восстановленными, пока нет проверенных поездов и регулярных автобусов.

После разрешения: завершить проверки конкретного коммита, слить PR, затем вручную запустить **Публикация сайта после проверки** на `main`, указав `production`. Workflow заново проверит этот же коммит, соберёт клиент и передаст проверенный `dist` в job деплоя. Сборка сама по себе не подтверждает правильность расписаний.

Сначала проверьте вход и защищённый API на обоих адресах. Только после отдельного разрешения выполнить **Обновление расписания** с `mode=full` и `confirm=publish`. Проверьте ответ API, источники, даты, цены и ссылки. Таймер включается последним.

## Таймер и частота

`wrangler.scheduler.toml` поставляется с выключенным Cron. Отдельный Cloudflare Worker делает `workflow_dispatch` в существующий GitHub collector. Он проверяет, что workflow включён, не накапливает запуски при занятом collector и не отправляет повторный запрос того же десятиминутного интервала. Если полный сбор в текущем часу ещё не прошёл, следующий свободный интервал выполняет его.

- Ближайшие три даты: каждые 10 минут.
- Остальные даты до горизонта 30 дней: примерно раз в час.
- Нативные scheduled workflows GitHub удалены из новой конфигурации. Ранее collector был отключён по неактивности; перед активацией нового таймера требуется проверить/включить workflow в GitHub.
- Просроченный запуск с ожидавшим более десяти минут слотом отказывается от сбора.
- Сбор конкретного источника ограничен 90 секундами в ближнем режиме и 360 секундами в полном. HTTP-запрос ограничен временем включая тело, с максимум двумя дополнительными попытками для временных ошибок. 403/404 не повторяются; неизвестный или длительный 429 останавливает цикл источника.
- 5/8 минут — предел шага сбора в ближнем/полном режиме. Подготовка runner тоже занимает время; точное выполнение каждые десять минут бесплатный GitHub не гарантирует. Задержку ловит внешний монитор.

После отдельного разрешения настроить секрет `GITHUB_TOKEN`, опубликовать таймер и включить `[triggers]` с `crons = ["*/10 * * * *"]`. До этого момента автоматическое обновление не работает.

## Что означает возраст данных

`generatedAt` — время сборки общего снимка. Оно не означает новую проверку каждого рейса. `lastSeenAt` и временные отметки вариантов бронирования сохраняют фактический возраст наблюдения.

Цена и места старше 15 минут становятся неизвестными. При сбое источника ранее известные места также не показываются доступными. Последнее известное расписание сохраняется до семи дней только для будущих отправлений и явно помечается. Рейсы старше этого срока исключаются. Цена относится к выбранному продавцу; места разных продавцов не складываются.

Успешная пустая выдача конкретного источника/направления/даты удаляет его предыдущие предложения. Отсутствующий, повреждённый или заблокированный ответ не означает «рейсов нет». Поломка одного источника не стирает данные остальных.

## KV, резерв и квоты

Два версионных снимка проверяются до переключения `manifest:active`. Сам manifest содержит ссылки на предыдущую версию. Частые версии живут шесть часов. При полном сборе обновляются две устойчивые копии `backup:*` со сроком хранения семь дней. Их временные отметки рейсов не изменяются. KV распространяет изменения не мгновенно; API использует прошлую версию/резерв, если новый снимок ещё недоступен.

Запрещается переключать manifest, если ни один источник не подтвердил данные, запись KV не подтверждена, данные имеют неверную схему/ссылки, размер одного направления больше 2 MiB или сравнимые будущие предложения сократились больше чем на 60% при исходном количестве не менее десяти. Последний случай требует расследования, включая законное отсутствие рейсов; качество не «лечится» отключением проверки.

Плановый бюджет: 144 цикла × 3 записи + 24 полных цикла × 2 резервные записи = около 480 KV-записей в сутки. Повторы и ручные запуски добавляют записи. Проверить реальное число записей, объём хранения и расход CPU после пробного выпуска. Лимиты аккаунта разделяются с другими проектами; платный тариф автоматически не включать. Ограничение в 2 MiB — защита бюджета, а не доказательство, что полный сбор уже помещается в него.

## Бесплатные уведомления на email

После согласования адреса владельца подключить бесплатные HTTP-мониторы UptimeRobot и email-уведомления GitHub Actions. Учётная запись мониторинга и тестовые письма ещё не создавались.

| Проверка | URL / правило | Порог |
|---|---|---|
| Основной сайт и зеркало | Корень каждого адреса | Проверка каждые 5 минут; ошибка HTTP/таймаут. |
| KV, снимки и collector | `/api/health` на обоих адресах | 503 при возрасте цикла больше 20 минут или отсутствии снимка. |
| Дальний горизонт | `/api/health?check=full` | 503, если нет подтверждения дальних дат за 75 минут. |
| Каждый импортируемый источник | `/api/health?source=avtoslava` и аналогично по id | После второго неполного ближнего цикла либо возраста последнего подтверждения больше 20 минут. |
| GitHub Actions | Встроенные email-уведомления владельца | Неуспешный collector/deploy, в том числе запрет публикации при падении количества больше 60%. |
| Ссылка продавца | Ручная выборка или разрешённая HTTP-проверка | Только подтверждённый 404/410 означает сломанную ссылку. CAPTCHA/403/таймаут означают неизвестный результат. |

Публичный health не содержит рейсов, ключей или сведений о пассажирах. Email-адрес и настройки сервисов согласуются перед включением. Не включать платные функции мониторинга.

## Если пришло уведомление

1. Открыть GitHub → Actions → последний collector. Прочитать статусы источников и причину ошибки.
2. Если не было запуска: проверить Worker-таймер, включён ли workflow, срок GitHub-токена и очередь jobs.
3. Если Cloudflare ответил 401/403: проверить срок и права токена, выбранный аккаунт и namespace. Не печатать токен в журнал.
4. Если один перевозчик недоступен: не отключать проверки данных; показать последние известные данные с возрастом и дождаться допустимой проверки или официальной интеграции.
5. Запустить read-only **Диагностика KV без публикации**. Она отдельно показывает наличие manifest, активных ссылок и резервов.
6. Ручной повтор публикации — только после устранения причины, с разрешения владельца.

Не решайте ошибки повторным включением демонстрационных данных или искусственным обновлением времени старых рейсов.

## Откат

Остановить таймер и новые публикации. При проблеме данных вернуть проверенную предыдущую пару снимков, сохранив их возраст, или восстановить устойчивый резерв. При проблеме кода вернуть последнюю проверенную версию с серверной защитой и без демо-подмены. Исходный выпуск со скрытием ошибок демонстрационными рейсами не считается безопасным откатом.

Сначала резервировать действующую конфигурацию, текущий manifest и точный SHA выпуска. Любая запись production-KV, изменение конфигурации или деплой отката требует разрешения владельца. Отозванные ключи при откате не восстанавливать.

## Приёмка в Беларуси

На домашнем ПК и телефоне через мобильного оператора, без VPN: открыть оба адреса, войти, проверить оба направления и несколько дат, фильтры трёх видов транспорта, сортировку, неизвестные цены/места, переходы продавцам, выход и отзыв ключа. Сопоставить выбранные реальные рейсы с продавцом. Записать дату, сеть и результат без раскрытия ключей.

После запуска собрать семь дней наблюдений. Цели согласованного плана: доступность не менее 99% за этот период и нормальный возраст ближних наблюдений до 15 минут. Это цели приёмки, пока не доказанные измерениями.
