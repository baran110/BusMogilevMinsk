# Автообновление

Владелец 14 ноября отдельно поручил возобновить автообновление самостоятельно. Подготовлено штатное расписание GitHub Actions, использующее существующий dispatcher из `scheduler/index.ts`. Постоянный токен не создаётся и не запрашивается: временный GITHUB_TOKEN имеет только Actions write и Contents read текущего репозитория. Worker-планировщик Cloudflare остаётся выключенным, чтобы не было двух таймеров.

`.github/workflows/schedule.yml`: минуты UTC 03, 13, 23, 33, 43, 53; для Минска те же минуты. Это целевое расписание, не гарантия времени. Просроченная более чем на десять минут задача не отправляет запросы сборщикам. Сами сборщики повторно проверяют свои слоты перед работой. Dispatcher использует текущие слоты после установки зависимостей, независимо проверяет занятость основного и дальнего workflow и не повторяет один слот/час.

Первый успешный полный сбор каждого часа обновляет дальние даты остальных источников; далее выполняется near. Дальняя БЖД — не более одного автоматического запуска в час, включая неудачные попытки. Дальний job не блокирует обновление остальных источников. Полный и ближний сборы используют одну группу concurrency; таймер — отдельную группу, исключающую одновременные dispatcher.

После Verification/HTTP403/HTTP429 БЖД оба её производителя читают общий часовой перерыв из существующих подтверждённых пакетов. Во время перерыва запросов к БЖД и перезаписи её пакетов нет; остальные источники продолжают обновляться. Исходные времена и error coverage сохраняются, отсутствующие поезда не объявляются подтверждённой пустотой. Окончание перерыва не означает снятия ограничения: очередной штатный цикл может снова остановиться на challenge. CAPTCHA и ограничения не обходятся.

Bootstrap теперь дожидается обоих начальных workflow и выполняет завершающий near даже при ошибке дальней БЖД; затем сообщает AggregateError и сохраняет неуспешный статус первоначальной операции. Ошибка источника не скрывается успешной публикацией остальных данных.

## Проверка и обслуживание

В Actions проверить «Автообновление расписания»: первый push-запуск, затем отдельный event=schedule. Успех dispatcher подтверждает только отправку/пропуск занятой или дублирующей задачи; требуется проверить conclusion дочерних сборщиков, новый manifest и `/api/health` обоих доменов. `/api/health?source=bzd&check=full` должен отдельно показывать проблемы дальней БЖД. Полная матрица API описана в API_SMOKE_RU.md. Фактические run IDs и результаты включения фиксируются в отчёте после выполнения.

В public-репозиториях GitHub отключает schedule после 60 дней без активности; точные интервалы и отсутствие пропущенных событий не гарантированы. Это ограничение выбранного запуска, а не устранённая причина прежней остановки навсегда. При отключении владелец с write-доступом включает workflow в Actions или меняет cron. Автоматические фиктивные коммиты для поддержания активности не создаются. Для независимого Cloudflare Cron позднее понадобится отдельный ограниченный постоянный токен; одновременно два таймера не включать.

Остановка: Disable workflow у «Автообновление расписания»; уже отправленные дочерние run нужно проверить отдельно. Откат кода — revert PR автообновления, сохранение ключей/SESSION_SECRET и существующих безопасных снимков. Удалять KV или восстанавливать октябрьский manifest с отсутствующими снимками не нужно.

Используются стандартные ubuntu-latest runners публичного репозитория, без paid runners, новых сервисов или платных настроек. Таймер не создаёт артефакты; постоянные секреты не меняются. Расчёт штатных записей KV около 768 ключей/сутки — прежняя оценка, не измерение аккаунта; перерыв БЖД уменьшает число её записей. Фактические квоты аккаунта следует измерять отдельно.

Официальные ограничения: [schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), [временный токен](https://docs.github.com/en/actions/concepts/security/github_token), [стоимость стандартных public runners](https://docs.github.com/en/billing/concepts/product-billing/github-actions).
